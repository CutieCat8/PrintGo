# A3: Payment API และ PaymentPanel — งานระหว่างพัฒนา

Branch A3 รวม A1/A2 และ PR #12 เพื่อใช้ UI ของยูริและ domain/API ของพลุในเครื่อง
ไม่ได้ merge PR ของเพื่อนเข้า main
รอบเชื่อมหน้าลูกค้าใช้ branch `feat/a3-payment-panel-integration` ต่อจากธุรกรรมกลาง
เปลี่ยน PaymentSection ให้ใช้ PaymentPanel แล้วตามอนุมัติ ต้องให้ยูริรีวิวก่อน merge

## ส่วนที่ทำแล้ว

- POST `/api/payments/orders/:orderId/charge`: ตรวจลูกค้าเจ้าของออเดอร์ อ่านยอดจาก DB
  และใช้ primary key ของ attempt ที่คำนวณซ้ำได้ เพื่อป้องกันสร้างแถว pending ซ้ำเมื่อเรียกพร้อมกัน
- POST `.../slip/sign`: signed upload ไป bucket payment-slips แบบ private ไม่ upsert
- POST `.../slip`: ตรวจพาธ UUID ในโฟลเดอร์ของออเดอร์ ชนิดไฟล์ signature และขนาดจริงไม่เกิน 5 MB
  ตรวจหมดอายุก่อนรับสลิปและซ้ำหลังดาวน์โหลด จอง attempt ด้วย conditional update
  `pending -> pending_review` ก่อนตรวจสลิป เพื่อไม่เรียก provider ซ้ำเมื่อส่งพร้อมกัน
- ส่งสลิปที่ถูกปฏิเสธได้รวม 5 attempts ต่อออเดอร์ (นับจาก payments ที่บันทึกไว้)
  ส่งพาธเดิมซ้ำคืนผลเดิม ไม่ตรวจซ้ำหรือสร้าง attempt เพิ่ม
- PaymentPanel ใช้ UI และ authenticated client ของยูริ แสดง QR ยอดจาก charge API
  นับถอยหลัง พรีวิว/ลบ/อัปโหลดพร้อม progress และ poll สถานะทุก 4 วินาที
- `/dev/payment` เป็นหน้าทดสอบที่ผู้ใช้อนุมัติให้เพิ่มนอกโฟลเดอร์อาร์ม
  มีเฉพาะ NODE_ENV=development รูปบัญชีและผลทั้งหมดเป็นตัวอย่างสมมติ ไม่เรียก API จริง

## ข้อที่ยังไม่ผ่านเกณฑ์ A3

**ธุรกรรมส่วนกลางมี implementation แล้วบน branch `feat/a3-atomic-transactions`**:
`finalizePayment()` ใช้ validation เดียวกับ `transition()` และ RPC `transition_order_finance`
เพื่อบันทึก payment verified + paid + settlement พร้อมกัน คืนเงินจากการยกเลิก/ปฏิเสธ
ก็ใช้ RPC เดียวกัน ตรวจสถานะ/ยอด/deadline ใต้ row lock และไม่แจ้งเตือนซ้ำเมื่อ replay
ต้อง apply migration ก่อน deploy code นี้ และให้ซี/พลุรีวิวไฟล์ข้ามเจ้าของ

`getPaymentService()` ต่อ finalizer จริงแล้ว แต่ยังใช้ O9 เป็น pending_review ตามเดิม:
ไม่ได้ยืนยันบัญชีสาขา SlipOK แทนซี จึงยังไม่เปิดรับเงินจริงโดยอัตโนมัติ
A6 ต้องเรียก `finalizePayment({ orderId, paymentId, verifiedBy: 'admin' })`
แทนการ update payment แล้วเรียก transition แยกกัน

ทดสอบ RPC กับ PostgreSQL 17 จริงใน Docker แยก ไม่มีข้อมูลจริง:
ตรวจ rollback/การเรียกพร้อมกัน/สลิปซ้ำ/สิทธิ์ ดู `ATOMIC-FINANCE.md`
การทดสอบนั้นยังไม่ใช่ Supabase Auth/Storage/PostgREST หรือ SlipOK จริง
ถ้า transaction ล้มหลัง provider ตรวจแล้ว สลิปยังอยู่ pending_review ให้ตรวจด้วยมือ
การส่งพาธเดิมซ้ำไม่เรียก SlipOK ซ้ำ (สำคัญเมื่อใช้ log:true)

ก่อนปิด A3 ยังต้องตรวจหน้าลูกค้าที่เชื่อมแล้วบนเบราว์เซอร์จริงและทดสอบทั้ง flow
และตกลงกรณียกเลิก/หมดอายุขณะสลิปรอตรวจ (known issue ใน docs/API.md)
การอนุมัติ/คืนเงินของแอดมินยังเป็นงาน A6 ไม่ได้เพิ่มในงานส่วนกลางนี้

## วิธีตรวจหน้าจอ
