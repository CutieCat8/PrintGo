# A3: Payment API และ PaymentPanel — งานระหว่างพัฒนา

Branch A3 รวม A1/A2 และ PR #12 เพื่อใช้ UI ของยูริและ domain/API ของพลุในเครื่อง
ไม่ได้ merge PR ของเพื่อนเข้า main และยังไม่ได้เปลี่ยน PaymentSection ของยูริ
ให้ import PaymentPanel (ต้องให้ยูริรีวิวการเปลี่ยนตอนเชื่อมจริง)

## ส่วนที่ทำแล้ว

- POST `/api/payments/orders/:orderId/charge`: ตรวจลูกค้าเจ้าของออเดอร์ อ่านยอดจาก DB
  และใช้ primary key ของ attempt ที่คำนวณซ้ำได้ เพื่อป้องกันสร้างแถว pending ซ้ำเมื่อเรียกพร้อมกัน
- POST `.../slip/sign`: signed upload ไป bucket payment-slips แบบ private ไม่ upsert
- POST `.../slip`: ตรวจพาธ UUID ในโฟลเดอร์ของออเดอร์ ชนิดไฟล์ signature และขนาดจริงไม่เกิน 5 MB
  ตรวจหมดอายุก่อนรับสลิปและซ้ำหลังดาวน์โหลด จอง attempt ด้วย conditional update
  `pending -> pending_review` ก่อนตรวจสลิป เพื่อไม่เรียก provider ซ้ำเมื่อส่งพร้อมกัน
- ส่งสลิปที่ถูกปฏิเสธได้รวม 5 attempts ต่อออเดอร์ (นับจาก payments ที่บันทึกไว้)
  ส่งพาธเดิมซ้ำคืนผลเดิม ไม่ตรวจซ้ำหรือสร้าง attempt เพิ่ม
- PaymentPanel ใช้ UI และ authenticated client ของยูริ แสดง QR ยอดจาก charge API
  นับถอยหลัง พรีวิว/ลบ/อัปโหลดพร้อม progress และ poll สถานะทุก 4 วินาที
- `/dev/payment` เป็นหน้าทดสอบที่ผู้ใช้อนุมัติให้เพิ่มนอกโฟลเดอร์อาร์ม
  มีเฉพาะ NODE_ENV=development รูปบัญชีและผลทั้งหมดเป็นตัวอย่างสมมติ ไม่เรียก API จริง

## ข้อที่ยังไม่ผ่านเกณฑ์ A3

**ยังไม่เปิด auto-verified -> paid ใน production**: PR #4/#12 ยังเปลี่ยนสถานะออเดอร์
กับสร้าง settlement/refund แยกกัน หากขั้นหลังล้ม ออเดอร์อาจ paid แต่ไม่มีแถวเงิน
จึงไม่มีการนำลำดับนั้นมาใช้เพื่ออนุมัติเงินจริงจาก payment service นี้

`getPaymentService()` ใช้ O9 เป็น pending_review และไม่ยืนยันบัญชีสาขา SlipOK เอง
แม้ตรวจสลิปสำเร็จแล้ว service จะเก็บ slipRef รอตรวจ จนกว่าจะมี finalizer ส่วนกลาง
ที่ทำ payment verified + transition() + settlement สำเร็จ/ย้อนกลับพร้อมกัน
`finalizeVerified` ใน dependency injection เป็นจุดเชื่อมในอนาคตเท่านั้น
tests ที่จำลอง finalizer ไม่ใช่หลักฐานว่า transaction ใน Postgres จริงผ่านแล้ว
การอนุมัติสลิปด้วยมือในหน้าแอดมินเป็นงาน A6 และยังต้องใช้ transaction ที่แก้แล้วเช่นกัน

ก่อนปิด A3 ต้องให้พลุ/ซีทำส่วน transaction กลาง แล้วต่อ finalizer ที่เรียกผ่าน transition
และทดสอบ paid ครั้งเดียว settlement หนึ่งแถว รวมกรณี DB ล้มและคำขอแข่งกันบน DB จริง
ต้องตกลงกรณียกเลิก/หมดอายุขณะสลิปรอตรวจด้วย (known issue ใน docs/API.md ของพลุ)
ยังไม่ได้เปิด SlipOK จริงหรือรับเงินจริง และยังไม่ได้ทดสอบ API ชำระเงินกับ Supabase จริง

## วิธีตรวจหน้าจอ

รัน `npm run dev` แล้วเปิด `/dev/payment` เลือกรูปสมมติ JPEG/PNG
เลือกผลจำลอง ผ่าน/รอตรวจ/ไม่ผ่าน กดส่งได้โดยไม่มีการอัปโหลดออกไป
ปุ่มจำลองแอดมินอนุมัติใช้ตรวจ polling และ onVerified ไม่ใช่การเปลี่ยนข้อมูลจริง
ห้ามใช้ภาพสลิปจริงใน story นี้
