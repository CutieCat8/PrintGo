# A4 — บันทึกโอนให้ร้านและคืนเงิน

## ขอบเขต

- `/admin/settlements` รวมรายการตามร้าน แสดงยอดรอโอน/โอนแล้ว และลิงก์ออเดอร์
- `/admin/refunds` แสดงผู้รับ เหตุผล ยอดคืน และสถานะ
- สถานะเริ่มต้น pending เลือก paid/all ได้ ยอดรวมคำนวณจากรายการที่ตรงตัวกรอง เป็น integer satang และปฏิเสธผลรวมเกิน safe integer
- เฉพาะ admin เรียก API/เปิดหน้าได้ ใช้ guard/origin/private-no-store เดียวกับ A6
- UI ให้ตรวจผู้รับและยอดหลังโอนสำเร็จ แล้วบันทึกทีละรายการตาม default ของ task A4 และ O4

## API และความสอดคล้องของเงิน

- `GET /api/admin/settlements?status=pending|paid|all` คืน `shops` ซึ่งมีรายการต่อร้านและยอด pendingSatang/paidSatang พร้อมยอดรวมของผลลัพธ์
- อ่าน settlements ด้วย inner join และกรอง orders.status=completed ตั้งแต่ฝั่ง DB ออเดอร์ cancelled/rejected/ยังไม่เสร็จไม่เข้าในรายการ
- `POST /api/admin/settlements/:id/mark-paid { proofPath? }` ตรวจออเดอร์ completed ร้านตรงกัน และยอดตรง print_subtotal_satang ก่อน conditional update pending→paid
- completed เป็น terminal ตาม transition จึงไม่มีเส้นทางแอปเปลี่ยนสถานะกลับขณะบันทึกการโอน
- เวลา paid_at และ proof_path บันทึกครั้งเดียว การเรียกซ้ำคืน changed=false โดยคงค่าของผู้ชนะเดิม
- proofPath เป็น relative object path แบบ optional ใน API ยังไม่มีฟอร์มอัปโหลดหลักฐานใน UI รอบนี้ การทดสอบใช้พาธหลักฐานสมมติ
- `GET /api/admin/refunds?status=pending|paid|all` คืน refunds และยอดรวมของผลลัพธ์
- `POST /api/admin/refunds/:id/mark-paid` รับ body ว่างหรือ {} ตรวจออเดอร์ cancelled/rejected/expired และยอดคืนไม่เกิน total จาก DB ก่อน conditional update
- การสร้าง settlement/refund ยังคงเป็นงาน A3/A6 ผ่าน transition และธุรกรรมกลาง A4 บันทึกผลการโอนของรายการที่มีอยู่
- keyset pagination อ่านเกินขีดจำกัดหน้าแรกได้ ไม่มีการจำกัดผลลัพธ์เงียบ ๆ ไว้ที่ 100/1000 รายการ

## หลักฐานการทดสอบ

- lint/typecheck ผ่าน tests ทั้งโปรเจกต์ 1110 ผ่าน / 15 ข้าม (14 PostgreSQL opt-in เดิม และ 1 QR preview manual)
- เพิ่ม 31 tests ครอบคลุมยอดต่อร้าน การกรอง completed สถานะไม่พร้อม/ยอดไม่ตรง การเรียกพร้อมกันและ replay ที่ไม่เขียนเวลา/หลักฐานใหม่ ข้อผิดพลาด DB สิทธิ์ origin input พาธหลักฐาน และ SSR ของรายการ
- unit tests ใช้ query imitation จึงตรวจ PostgreSQL/PostgREST เพิ่มผ่าน Next dev กับ PrintGo-dev จริง โดย guard URL ของโปรเจกต์ไว้ในสคริปต์ชั่วคราว
- ตั้งต้นออเดอร์ completed/cancelled/rejected/paid, settlement และ refund เป็นข้อมูลสมมติ ตรวจ API ได้ยอดตามร้านตรงและไม่รวม settlement ของออเดอร์ไม่เข้าเงื่อนไข
- API ปฏิเสธ mark-paid ของ cancelled/rejected/paid ด้วย 409
- สองคำขอ settlement mark-paid พร้อมกันตอบ 200 ทั้งคู่ changed=true เพียงคำขอเดียว เรียกซ้ำคง paidAt/proofPath เดิม
- refund mark-paid พร้อมกันมีผู้ชนะหนึ่งคำขอ และ replay คง timestamp
- anonymous ได้ 401, shop ได้ 403 การทดสอบ admin API ในรอบนี้ใช้ x-dev-user เฉพาะ development
- ล้าง customer/shop/order/settlement/refund สมมติทั้งหมดใน finally แล้ว การทดสอบนี้ไม่มีการเรียกผู้ให้บริการโอนเงิน

## การตรวจหน้าจอด้วย session จริง (13 พ.ย. 2026)

- ใช้บัญชี admin สมมติชั่วคราวและ Supabase session จริงใน PrintGo-dev ผู้ใช้กดยืนยันขั้นสุดท้ายเอง ไม่มีการโอนเงินจริง
- หน้ารอโอนแสดงเฉพาะสองออเดอร์ completed รวม 140.00 บาท ไม่แสดงออเดอร์ cancelled/paid ที่ยังไม่เสร็จ
- ผู้ใช้บันทึก PG-0016 จำนวน 120.00 บาท ตรวจ DB เป็น paid และหน้ารอโอนเหลือ PG-0017 จำนวน 20.00 บาท เวลา paid_at ของ PG-0016 คงเดิมเมื่อตรวจอีกครั้ง
- หน้าคืนเงินแสดงผู้รับ เหตุผล และ PG-0018 จำนวน 50.00 บาท ผู้ใช้ยืนยันแล้ว ตรวจ DB เป็น paid และหน้ารอโอนคืนเหลือ 0.00 บาท
- พบปุ่มยืนยันแบบ primary มองไม่เห็นใน browser จึงเปลี่ยนเฉพาะปุ่มของ A4 เป็น secondary ซึ่งใช้พื้น/ตัวอักษร/เส้นขอบเดียวกับปุ่มกลับ คง loading/disabled/handler เดิม lint/typecheck ผ่านหลังแก้ ผู้ใช้ยืนยันคืนเงินสำเร็จหลังการแก้
- reviewer ตรวจ A4 และการแก้ปุ่มแล้ว ไม่พบ blocker; รอบนี้ไม่ได้ตรวจตัวกรอง paid/all ผ่าน browser จึงอ้างผลตัวกรองจาก API/tests เท่านั้น
- ล้างและตรวจว่าไม่เหลือ 4 orders, 4 settlements, 1 refund, 1 shop, 1 customer และบัญชี admin/profile สมมติชั่วคราวแล้ว
